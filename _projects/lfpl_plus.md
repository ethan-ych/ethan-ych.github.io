LFPL stands for Linear Functional Programming Language. It is a programming language introduced by Martin Hofmann in 1999. By adopting a substructural type system, it defines a curious subset of programs - those that run in polynomial time. In other words, every program you are able to write in LFPL will run in polynomial time, and you can write every polynomial time program in LFPL. I will lay out some intuition for why every LFPL program will run in polynomial time. To understand this, we first need to understand what a substructural type system is. It is likely the case that every programming language you have learned in your life is structural, i.e. it allows weakening and contraction. In simpler terms, the typechecker allows a program to throw away unused variables and freely reuse variables. This might seem entirely natural for a type system, but it needs not be the case. 

If you take away weakening, you get a *strict* type system, which enforces every variable to be used at least once. If you take away contraction, you get an *affine* type system, which enforces every variable to be used at most once. If you take away both, you get a *linear* type system, which enforces every variable to be used exactly once. This is how a programming language can be aware of the resource usage from the input. LFPL has an affine type system. It introduces this concept of *diamonds* that can be used at most once, and there are no expressions in the syntax that let you "spawn" a diamond. As a consequence, within the body of a (top-level) LFPL function, you can't ever have more diamonds than those already exist in the input. What are the diamonds used for? You need a diamond to prepend an element to a list, or from another perspective, lists implicitly contain a diamond for each element they have. 

Now comes the neat part. You only have one kind of recursion/iteration in LFPL - a list recursor. No general recursion, no arbitrary for loops. If you're familiar with functional programming languages, imagine you only have *fold* but no recursion, and if you're more familiar with imperative languages, imagine you only have *for each* loops (and still no recursion). Combined with the scarcity of diamonds, we can only ever recurse through lists that are as long as the input lists over and over again. If the input list has size $n$, you can only write programs that run in $O(n)$ with naive use of recursors. You can write nested recursors but that will give you $O(n^k)$, which is still polynomial in input size. That's it for why you can only define programs that run in polynomial time (the actual proof uses a notion of the *size* of an expression, which is much more formal and complex than the intuition here). 

I wanted to make it clear that LFPL is entirely of theoretical interest and not meant for practical use (though my partner Kandasamy and I did imagine a day when Amazon adopts LFPL). In fact, researchers in the past tried to define languages like LFPL to indirectly prove $\mathsf{P} \neq \mathsf{NP}$, but as you might've guessed it didn't work out. Kandasamy and I implemented an interpreter for LFPL as the final project for *15-714 Resource Aware Programming Languages*, and by doing so we brought this language to life. 

Having implemented a C0 compiler in another class made implementing an interpreter a pleasant experience. The most interesting part was definitely studying how to implement an *affine* typechecker, since it wasn't obvious from the typing rules. I also thoroughly enjoyed augmenting the language by adding new expressions and syntactic sugars, delivering LFPL+. All in all, implementing a new language from end to end and resolving various blockers on the way was much more fun and rewarding than I thought.
